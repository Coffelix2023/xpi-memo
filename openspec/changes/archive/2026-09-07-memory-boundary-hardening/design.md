## Context

See `proposal.md` - Why. 当前 `content-policy.ts` 已有部分拒绝和导出脱敏逻辑，但召回渲染、工具结果、外部 runner 输入和诊断字段尚未形成同一条安全边界。L0 是本地可重放事件真源，不能为了脱敏而改写历史；T1、Mnemosyne、provider runner 和模型可见输出都必须使用经过安全处理的副本。

## Goals / Non-Goals

**Goals:**

- 建立一个供所有记忆可见入口复用的安全处理契约，统一阻断、脱敏、计数、原因类别和策略版本。
- 用高精度本地规则阻断明显提示注入，按条目处理，避免单条风险扩大为整批不可用。
- 在外部传输前生成安全副本；已知凭证脱敏，安全状态不确定时不发送。
- 用有界元数据解释阻断、预算省略和外部拒绝，并兼容已有 L0 事件。
- 保持非 TUI、自动召回和现有治理流程可诊断，不把安全失败伪装成存储成功。

**Non-Goals:**

- 不修改 L0 的 lossless 本地保存约定，不做历史事件迁移。
- 不修复 L0/T1 双写顺序、Markdown 游标、全量投影重建或删除同步；这些属于独立一致性 change。
- 不引入 `pi-memory-mem0`、`pi-hermes-memory` 或新的安全规则依赖。
- 不直接调用当前未向扩展公开的 `completeSimple()`，不新增 direct runner。
- 不实现 Standing Instructions、周期 review、`observedAt`、自动 dedup 删除或 UI 视觉层。

## Decisions

### 1. 共享安全模块，而不是各入口各写一份规则

新增一个小型内部安全处理边界，接收记忆条目或待外发文本，并返回安全结果：可用安全内容、被阻断条目、脱敏状态、原因类别、计数和策略版本。自动召回、`xpi_memo_recall`、`xpi_memo_show_injected` 与 context preview 只负责把结果转换成各自的显示外壳。

这样可以保证规则不会因入口分叉。模块保持无状态，不保存正文，不承担召回排序、治理、存储或 UI 职责。

备选方案：每个入口分别处理。它初期改动较少，但无法保证未来入口不会漏过保护。

### 2. L0 原文与外部安全副本严格分离

L0 记录仍按现有 lossless 合约追加，供审计和重放使用；任何发送给 Mnemosyne、Track B runner、其他 provider 或模型可见结果的内容，都必须来自安全处理模块输出。脱敏不得回写 L0 历史事件，也不得让调用方从原始字段重新组装外部 payload。

安全处理失败时，调用方记录有界失败状态并停止外部调用。该失败不自动删除本地事件、不伪装成 T1 成功，也不触发未经授权的重试。

备选方案：写入 L0 前统一脱敏。它能减少本地敏感数据，但会破坏当前事件真源的可重放语义，本 change 不采用。

### 3. 召回采用高置信度、逐条阻断

首版只实现小型本地规则，覆盖明显的提示注入命令式表达，例如要求忽略既有指令、改变系统规则或执行命令的模式。规则命中单条记忆时仅移除该条正文，保留同批次未命中的安全条目；模糊内容依赖不可信数据边界，不由低置信度规则扩大阻断。

备选方案：整批阻断会放大误报影响；只加警告不能提供足够的主动防护；引入第三方规则库增加依赖和维护面。

### 4. 凭证策略是“可识别则脱敏，不确定则拒绝外发”

外部传输前复用或提取现有本地脱敏规则，覆盖常见 token、API key、密码和凭证格式。处理结果必须明确区分安全、已脱敏和拒绝外发。无法可靠确认安全时，调用方不得发送原文或猜测性安全副本。

该策略只约束外部边界；`MEMORY.md` 继续使用已有 privacy 导出策略，本 change 只增加回归验证，不重构投影系统。

备选方案：全部拒绝会损失不含凭证的有效上下文；尽量脱敏后全部发送会把漏检风险转嫁给 provider。

### 5. 诊断使用可选字段和固定有界枚举

在 `memory_injected` 相关类型中增加可选诊断字段，至少表达成功注入数、阻断数、省略数、省略原因、策略版本和生命周期阶段。外部拒绝使用原因类别和“未执行”结果，不记录正文、完整输入、匹配片段或可恢复凭证。解析历史事件时对缺失字段采用明确默认值。

备选方案：迁移所有旧事件会增加风险；只保留 ID 无法解释安全处理结果；记录阻断正文会扩大泄露面。

### 6. 安全失败不自动重试外部请求

安全处理在外部请求发出前完成。安全拒绝不发送请求；本 change 不改变 provider 已发出但结果未知时的重试语义，也不新增 fallback。这样避免把安全失败和网络失败混淆，并避免重复计费。

## Risks / Trade-offs

- [Risk] 高精度规则会漏掉新型提示注入 → Mitigation：保留明确的不可信数据边界，记录有界策略版本和计数，后续根据诊断增加规则。
- [Risk] 本地 L0 可能包含敏感原文 → Mitigation：保持文件权限约束，禁止原文出域，诊断和日志不记录正文；后续可单独讨论加密存储，不在本 change 偷改 lossless 合约。
- [Risk] 入口接入不完整会留下旁路 → Mitigation：为自动召回、两个工具、context preview、外部 runner 和导出分别增加回归场景，并通过搜索确认调用方统一经过安全模块。
- [Risk] 旧事件缺少诊断字段 → Mitigation：新增字段全部可选，解析时使用固定默认值，不做历史迁移。
- [Risk] 现有导出脱敏规则与新外部规则产生差异 → Mitigation：本 change 先复用已有能力和测试；差异化规则演进留给独立策略 change。

## Migration Plan

1. 先加入安全结果类型、策略版本和高置信度本地规则，并为共享处理模块添加单元测试。
2. 逐个接入自动召回、显式 recall、历史注入查询、外部 runner/provider 和 `MEMORY.md` 导出边界。
3. 增加旧 `memory_injected` 事件读取测试、阻断/脱敏/拒绝外发测试和非 TUI 诊断测试。
4. 通过 `pnpm typecheck`、`pnpm -w run lint` 和 `pnpm test` 后启用行为。
5. 回滚时移除各入口对新处理模块的调用并保留兼容字段解析；不删除已有 L0 事件或改写外部存储。
