# 针对`docs/evaluation-reports/feedback-2026-09-03.md`真机实测反馈的优化意见

这份报告质量很高——实机端到端 + 逆向 mnemosyne 源码取证 + 历史 audit 审计三角互证。我的结论分两层：**这份报告实际上宣告了 xpi-memo 第一阶段（纯正则热路径捕获）的实验失败，但失败的方式非常有价值**；以及，它把我们之前讨论的三个悬而未决的设计决策（LLM 提取、Markdown 真相源、L2 延迟处理）从"该不该做"变成了"数据已经替你做了决定"。

---

## 一、核心结论：这不是三个孤立缺陷，是一条因果链

把报告的三个发现连起来看，它们构成一条完整的死亡螺旋：

```
缺陷 B（闸门词表不一致）
  → 自然表达漏捕获（14 探针漏 4，真实对话漏记率更高）
    → audit: 几乎零写入（113 条 audit 里仅 1 条确认记忆）
      → recall 104 次全部 0 命中
        → 用户感知零价值
          → 唯一一条记忆 1 分钟内被用户删除 + 6 次 sleep 授权全拒
            → 信任崩塌
              → 缺陷 A/C（forget 删不掉项目记忆、recall 无 id）在此刻补刀：
                 用户连"清理错误记忆"的能力都没有
```

报告 §4 的定性非常准：**"能力就绪、价值未兑现"**。链路全通（写-读-隔离-幂等-审计全绿），但价值闭环的每一个环节都在真实使用中断裂。这比"链路不通"的诊断残酷得多，也有用得多——它说明**架构骨架是对的，死的是血肉**。

## 二、数据替三个悬案做了裁决

这份报告最重要的价值，是为我们前几轮讨论中三个"可以再等等"的决策提供了终局证据：

**① 悬案一：§8.5"禁止 LLM 提取"——数据已裁决，闸门条件已满足。** 计划 v2 里我建议把"禁用 LLM"从禁令改为带触发条件的门："2 周 Track A → 采样 20 个会话 L0 → 若 >30% 有价值内容漏捕获则激活 Track B"。现在报告给了实测数字：14 组探针漏 4 组（29%），且漏的全是高频自然表达模式（"我偏好…"/"本项目禁止…"/"本仓库使用…"）；历史 audit 证明真实使用中自动捕获产出≈0。**触发条件已经事实上满足**。纯正则路线的上限已经被摸到了——闸门词表与类别词表的不一致（缺陷 B）只是症状，病根是"显式标记词"这个前提本身在真实中文对话里不成立：人不会说"请记住"，人说"我习惯…"。

**② 悬案二：Markdown 真相源 vs SQLite 真相源——缺陷 A/C 是 SQLite 真相源的结构性代价。** forget 删不掉项目记忆的根因是什么？是"bank 路由信息只存在于写入路径的运行时上下文里，删除路径要重新推导一遍"——remember 走 `routeMemoryKind`，forget 没走，于是两条路径不一致。这类 bug 在"数据库即真相"架构下会反复出现（每个操作都要重新推导路由）。如果记忆行的 metadata 里就持久化了 bank 归属（或如 ai-memory 那样 db 只是派生索引、真相在带完整元数据的 Markdown），删除路径就不需要推导任何东西。**缺陷 A 不是漏传参数的小错，是架构让"正确"需要每个调用点各自努力的结果。**

**③ 悬案三：104 次 recall 全 0——召回侧"高-value-auto 策略"同样被证伪。** 注意这个细节：recall 被调用了 104 次（说明 before_agent_start 注入机制在正常工作、在被触发），全部空返。这不是召回策略太严，是**库里根本没有货**。供给端（捕获）死了，需求端（召回）再精巧也是空转。优先级排序因此非常清晰：**先修供给，再谈排序。**

## 三、优化路线图（按依赖关系排序，非简单优先级）

### P0（本周，纯缺陷修复，无设计争议）

1. **缺陷 A + C 一起修**（它们是同一个闭环的两端）：forget 通过记忆行持久化的 bank 元数据反查路由（不要重新推导），recall 返回真实行 id。补 project 场景集成测试——`real-cli.integration.test.ts` 的 forget 只测 global 是这次漏网的直接原因。
2. **缺陷 B 的最小修复**：废除独立闸门词表，改为"任一类别模式命中即视为显式意图"。同时把 4 组漏捕获探针固化为回归测试——这份报告的探针集本身就是最好的测试资产。
3. **doctor 增加三个新状态**：`ROUTING_REJECTED`（上一轮已提）、`RECALL_ZERO_STREAK`（连续 N 次召回 0 命中时报警——这次 104 连 0 居然没有任何告警面）、`SLEEP_DISABLED`。

### P1（两周内，激活 Track B——数据已授权）

4. **正式启动双轨提取**（计划 v1 的 B 轨）：在 compaction / session_shutdown 边界跑门控 LLM 提取，证据类型 `llm-extracted`（永不冒充 `explicit-user-statement`），产物进 candidates 走既有治理。正则轨道保留为快速路径。**这不是推翻 §8.5，而是 §8.5 自己设定的触发条件被实测满足了**——在计划文档里把这次评估报告引用为该条件的达成证据。
5. **召回注入可见化**（报告建议 3，我升格到 P1）：before_agent_start 注入时，在 TUI/RPC 响应里带一行状态（"注入 N 条记忆 / 无相关记忆"）。当前全静默意味着：即使将来有货了，用户依然感知不到，价值闭环仍然缺最后一环。

### P2（结构性，跟随 L2 设计一起做）

6. **bank 归属持久化进记忆行 metadata**，让所有操作（forget/export/migrate）不再需要重推导路由。这是缺陷 A 的根治而非补丁。
7. **L2 延迟处理层启动设计**，直接对标 ai-memory 的 capture→consolidate 架构：L0 events.jsonl 已是 capture，缺的是"会话末编译"。注意这与 Track B 是同一入口（session_shutdown），两者应该作为一个管道实现而非两个功能。
8. **Markdown 真相源迁移**维持 P2 不提前——但要保证 P0/P1 的所有新写入路径都带完整元数据，为将来"db 可重建"做准备。

### 明确不做

- **不扩充触发词表作为 LLM 的替代**（报告建议 4 的前半句我否决）：词表扩充是打地鼠，每修一个词漏十个句式，且不可度量。Track B 上线后正则轨道维持现状即可。
- **不优先做 sleep**：6 次授权全拒 + 上游依赖缺失，说明它离可用最远，且价值闭环不依赖它。

## 四、一个必须直面的大问题

报告最刺痛的一行是"唯一一条已确认记忆 1 分钟内被用户删除"。缺陷 A 修好后，要警惕一种解释惯性："用户删除是因为 forget 坏了/记忆不准"。但更可能的真相是——**那条记忆（偏好类）是用户不想被记住的东西，或者注入方式让用户不适**。建议在 Track B 上线后的下一次实测里，专门观察"用户删除记忆"事件的前因后果，把它作为和"有价值捕获率"并列的一级指标。记忆工具的终极目标不是捕获率最大化，是**用户愿意让它记住**——这是个信任产品，不是捕获产品。

**止损线仍然有效**：Track B 上线后 2-4 周，若"有价值捕获率 × 有效召回率"仍趋近零，按上一轮决策，认真评估外挂 ai-memory 作为 L2 乃至整体底座。这份报告让那一天更近了一点，但 P0 三项修复 + Track B 是 xpi-memo 应得的最后一次完整机会。
