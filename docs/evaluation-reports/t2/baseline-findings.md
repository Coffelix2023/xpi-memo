## 2. 三条结论

### 2.1 中文多跳是基线最明确的缺口
三条多跳场景**全部未命中答案**，但其中两条正好命中了 bridge（位次 1）——说明检索**找到了正确的中间证据**，缺的是「再走一跳」。

- `s-hop-01`：返回 `m-hop-01`（xpi-memo 代号是 petrel），没有走到 `m-hop-02`（petrel 的 embedding 档位）。
- `s-hop-02`：返回 `m-hop-04`（删除能力依赖上游精确 ID），没有走到 `m-hop-03`（遗忘流程）。

**对后续的意义**：这是「轻量证据图 / 关系召回」唯一的硬价值证据（任务 3.2 的边类型设计要覆盖的正是这种 bridge → answer 关系），也是候选排序时唯一能拉开差距的维度。单跳场景基线已经 100% 命中，候选在这些类别上没有提升空间。

### 2.2 召回候选存在但被阈值丢掉，且不回退补位
`s-mix-02`（query 含 CLI 参数与中文问句）返回**空结果**，而同义的 `--explain` 短句能命中。`--explain` 输出的阶段数据：

```
wm_primary:  raw_count=2, after_filter_count=1, kept_count=0, fallback_used=false
em_fallback: raw_count=0, after_filter_count=0, kept_count=0, fallback_used=true
```

即：候选过了 filter，却在最终打分/保留阶段被丢，episodic 层也没有可以补位的行，最终返回空。`retrieval.fallback` 因此为 `true`（降级不可用），但**用户侧只看到「没有记忆」，看不出「有候选被丢掉」**。

**对后续的意义**：这是任务 4.3「T2 不可用时回退现有搜索链的诊断字段」要暴露的东西——`kept_count=0 而 after_filter_count>0` 必须能从状态字段读出来，否则同类静默失败无法诊断。

### 2.3 误召回主要来自「同类别不同主题」，而非语义漂移
误召回率 40%，但看逐条记录，误召回的条目几乎都是**结构相似、主题不同**的同银行记忆（`project_continuity` 48.9% 最高：问检索层决策返回了日志层决策、时区缺陷等）。

**对后续的意义**：单纯提升语义相似度不会降低误召回，反而可能加重。候选评估不能只看 hit 提升，必须同时看误召回率；低权重重排（任务 3.2）是唯一不被这个模式反噬的改法。

## 3. 基线的可用性判断

- 单跳中文（偏好 / 项目连续性 / 中英混合）基线已接近可用：命中位次几乎全是 1。
- 多跳中文基线不可用（0%）。
- 证据链本身不是瓶颈：100% 的返回结果都能解出 kind 与 prov，说明**证据可追溯性已经是基线能力**，候选不需要在这里加分，只需要不破坏它。
