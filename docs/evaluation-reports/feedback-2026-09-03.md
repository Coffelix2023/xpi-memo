# xpi-memo 记忆体(扩展工具)使用评估报告

> 评估方式:源码审读 + 实机端到端调用(remember / recall / forget / sleep)+ 历史数据审计
> 评估时间:2026-09-03
> 环境:Pi Coding Agent 0.84.4 · mnemosyne-memory 3.15.1 · macOS
> 仓库版本:main @ bfb6e8b

## TL;DR(结论优先)

- **写-读主链路可用**:`xpi_memo_remember` → 落库 → `xpi_memo_recall` 能召回(global 与 project 双范围实测通过),幂等去重生效。
- **forget 存在真实缺陷**:项目(project)范围内的记忆**无法通过工具删除**,报 `Memory deletion failed.`。根因:xpi-memo 调用 mnemosyne CLI 的 `delete` 时未传 bank 参数,项目记忆存储在 `banks/project-*/mnemosyne.db`,删除却作用于默认库,必然找不到。手动补 `MNEMOSYNE_BANK` 环境变量后删除成功(复现与验证见 §5)。
- **激活循环(自动捕获)命中率低**:意图提取是纯正则,闸门触发词表与类别词表不一致,自然表达(无"记住/默认"等触发词)无法捕获,即使类别词("偏好"等)已命中。仓库自带测试仅覆盖带触发词的句子,未覆盖此盲区。
- **历史使用数据印证使用率低**:audit 中 104 次 recall 全部 0 结果;唯一一条已确认记忆 1 分钟内被用户删除;6 次 sleep 授权全部被拒。记忆体实际推动工作流的效果目前接近零。

## 2. 功能评估

### 2.1 四个工具实测结果

| 工具 | 实测结果 | 评价 |
| --- | --- | --- |
| `remember` | 写入成功(global 直接存、project 走候选后自动确认),返回 `id`/`kind`/`scope` | ✅ 链路完整 |
| `recall` | 能召回刚写入的记忆,返回 `score`/`kind`/`scope`/`provenance` | ✅ hybrid 检索可用 |
| `forget` | **project 范围失败**(`Memory deletion failed.`);global 范围成功 | ❌ 缺陷,见 §5 |
| `sleep` | 返回 `sleep-mode-not-configured` | ⚠️ 默认禁用属 fail-closed 设计,非缺陷;但启用路径依赖 mnemosyne 侧能力,实际不可用 |

### 2.2 路由与隔离

- **项目身份**:`identity.ts` 以 `sha256(git-common-dir)[:12]` 计算,实测本仓库复算结果与 xpi-memo 使用的银行(`project-p-9a5af0fe2a2b`)一致 ✅
- **范围隔离**:global 记忆只进默认库,project 记忆只进项目库;recall 时 global 库过滤非 global 类目行(`mnemosyne-backend.ts` Task 5.1 逻辑) ✅
- **会话隔离**:`session_context` 行仅在来源会话内可见,无 sessionId 的行永不浮出 ✅
- **幂等**:同一内容重复 remember 返回 `Memory already captured for this session.`,`idempotency.json` 记录 fingerprint+event+kind 复合键 ✅

### 2.3 自动捕获(激活循环)

- 实现:`memory-intent.ts` 纯正则提取,无 LLM 参与(热路径);global_preference/global_workflow 直存,project_* 走候选。
- 实测(14 组探针):10 通过 / 4 失败,失败均为**自然表达漏捕获**,见 §3。
- 触发词表两表不一致:`EXPLICIT_MARKER_PATTERN`(闸门)不含"偏好/禁止/仓库使用/技术栈",而 `PREFERENCE_PATTERN` / `PROJECT_FACT_PATTERN` 含——**类别已识别但被闸门拦截**。

## 3. 准确度评估

### 3.1 召回准确度

- 写入后即刻召回,`score` 0.47–0.57(hybrid:向量+全文),命中内容与查询语义匹配,无噪音 ✅
- 召回结果为**纯内容列表**,`id` 为 `null`——工具设计上未把数据库行 id 暴露给调用方,导致 forget 只能靠用户手动提供 id(而工具内部又不补 bank),这是 §5 缺陷的组成部分。

### 3.2 意图提取准确度(自动捕获)

| 输入(自然表达) | 实际结果 | 期望 | 判定 |
| --- | --- | --- | --- |
| 我偏好使用中文回复 | no-explicit-intent | global_preference | ❌ 漏 |
| 本项目禁止引入 ink 库 | no-explicit-intent | project_constraint | ❌ 漏 |
| 本仓库使用 FastAPI 技术栈 | no-explicit-intent | project-fact-requires-verification | ❌ 漏 |
| 每次提交前都要运行 pnpm typecheck | global_workflow | 同 | ✅ |
| 我们决定采用 typebox 声明工具 Schema | project_decision | 同 | ✅ |
| 注意:config.yaml 会被覆盖 | project_gotcha | 同 | ✅ |
| Always answer in English | global_preference | 同 | ✅ |
| 更正:改用中文 | correction | 同 | ✅ |
| 默认每次都要先跑测试,决定采用 vitest | ambiguous-intent(拒) | 同 | ✅(保守拒,可接受) |

**结论**:召回(读)准确度合格;自动捕获(写)召回不足,以"无触发词即不记"的保守策略为代价,牺牲了大量自然表达。漏记率在真实对话(无"记住"字样)中会显著偏高。

### 3.3 历史数据审计(准确度/使用率侧面)

audit.json 共 113 条:
- recall 104 次,全部 `resultCount: 0`(含 "restore project context…" 的会话级注入,连续多天 0 命中)
- candidate 1 条(已确认),随即 confirmation 1 条,**1 分钟后 rejection**(用户删除)
- sleep-authorization 6 次,全部 `rejected`(原因 `dedicated-sleep-model-unsupported`)

即:**记忆体在真实使用中从未成功喂回过任何一条上下文**,唯一写入被用户主动删除。

## 4. 推动性能(对工作流的实际效能)

定义:记忆体在多大程度上推动 Agent 工作流(上下文恢复、偏好遵循、减少重复提问、跨会话连续性)。

| 指标 | 观察 | 评级 |
| --- | --- | --- |
| 会话上下文注入 | audit 显示多次触发 recall("restore project context…")但全部 0 结果 → 注入为空块 | ✗ |
| 跨会话连续性 | 无任何历史记忆可恢复 → 连续性为零 | ✗ |
| 偏好遵循 | 用户删除唯一一条偏好记忆 → 无偏好可遵循 | ✗ |
| 激活成功率 | 自然表达漏捕获 + 历史 0 写入 → 自动捕获几乎无产出 | ✗ |
| 失败降级 | recall 无后端/无命中返回明确状态与 warning,不阻塞会话 | ✓ |
| 写入可审计 | 每次写/删/召回全部落 audit,可追溯 | ✓ |

**结论:推动性能目前接近零。** 根因不是链路不通(链路实测可用),而是:(a) 自动捕获漏记太多;(b) 用户真实使用中零命中导致零价值感知;(c) forget 缺陷进一步消耗信任。记忆体是"能力就绪、价值未兑现"状态。

## 5. 缺陷清单(含根因与验证)

### 缺陷 A(高):forget 无法删除项目记忆

- **现象**:对 project 记忆调用 `xpi_memo_forget` 返回 `Memory deletion failed.`;对 global 记忆则成功。
- **根因**:`src/index.ts` forget 工具体执行 `runtime.run(["delete", id], { dataDir })`,未传 `bank`;而 remember 通过 `routeMemoryKind` 把项目记忆写入 `banks/project-*/mnemosyne.db`(CLI 的 `MNEMOSYNE_BANK` 环境变量)。delete 缺 bank → 默认库中找不到 → 必失败。
- **验证**:
  1. `mnemosyne delete <id>`(默认库)→ `Memory not found`
  2. `MNEMOSYNE_BANK=project-p-9a5af0fe2a2b MNEMOSYNE_DATA_DIR=~/.pi/agent/xpi-memo mnemosyne delete <id>` → `Deleted`,库中行消失
- **修复方向**:forget 工具体需解析当前项目 bank 并注入(与 remember/recall 对齐),或从源 metadata 反查 bank;`real-cli.integration.test.ts` 只测了 global 场景(测试盲区)。

### 缺陷 B(中):意图提取闸门词表与类别词表不一致

- **现象**:含"偏好/禁止/仓库使用"的句子类别模式命中但闸门拦截,返回 no-explicit-intent。
- **根因**:`EXPLICIT_MARKER_PATTERN` 与 `PREFERENCE_PATTERN`/`CONSTRAINT_PATTERN`/`PROJECT_FACT_PATTERN` 各自维护,闸门词少(无"偏好/禁止/使用/仓库/技术栈")。
- **验证**:14 组探针,4 组自然表达漏捕获(见 §3.2 表格)。
- **修复方向**:闸门改为"类别模式命中即视为显式意图"(删除前置闸门或并入类别判定);同步补中文自然表达测试用例。

### 缺陷 C(低):recall 返回 id 恒为 null

- 现象:recall 结果 `id: null`,无法作为 forget 的输入。
- 根因:`mnemosyne-backend.ts` 结果映射丢弃 `row.id`。
- 影响:配合缺陷 A,用户侧"召回→删除"闭环断裂(即便补了 bank,也没 id 可用)。

### 非缺陷(预期行为,记录以免误判)

- **sleep 默认禁用**:`sleep-mode-not-configured` 是 fail-closed 设计(默认 `disabled`),需显式 `XPI_MEMO_SLEEP_MODE` + mnemosyne 侧模型支持才可用。
- **候选确认**:project_decision 等走候选后自动确认(阈值内),audit 可见 candidate→confirmation 记录,属设计。

## 6. 优缺点汇总

### 优点

1. **架构分层清晰**:L0 会话溯源(JSONL,append-only、10MB 轮转)/ T1 治理记忆(SQLite 银行)/ Markdown 派生视图三层分离,责任边界明确。
2. **证据与治理完备**:每次写带 evidenceType + provenance(来源可回溯到 L0 event);idempotency 防重;audit 全量留痕;全局库对非 global 类目行做过滤(防跨范围泄漏)。
3. **fail-closed 与降级友好**:无后端时 recall 返回明确状态 + warning,不阻塞会话;sleep 默认禁用;配置解析 fail-closed。
4. **双语言意图覆盖**:中英文触发词均有,correction 信号(更正/纠正)支持。
5. **可观测性**:状态面板、doctor 分类、候选摘要齐全,350+ 测试。

### 缺点

1. **forget 缺陷直接破坏"可回滚"承诺**(AGENTS.md 核心原则):项目记忆写入后无法通过工具删除,只能手动清库。
2. **自动捕获精度不足**:触发词表漏洞导致自然表达漏记,真实对话命中率低,是"激活率≈0"的主因之一。
3. **价值闭环未跑通**:历史数据 104 次召回 0 命中 + 唯一记忆被删 + sleep 全拒 → 用户感知不到价值,推动性能归零。
4. **测试盲区**:`real-cli.integration.test.ts` 的 forget 场景只用 global 记忆,project 银行路径无覆盖;意图测试全用带触发词的句子。
5. **召回结果无 id**:破坏"召回→操作"闭环,工具间衔接设计不完整。
6. **sleep 依赖上游能力**:授权被拒路径(6 次 `dedicated-sleep-model-unsupported`)说明默认安装无法启用 consolidation。

## 7. 建议(按优先级)

1. **修复缺陷 A + C**(forget bank 注入 + recall 返回 id),补 project 场景集成测试——否则"可回滚"原则不成立。
2. **修复缺陷 B**(闸门并入类别判定),补中文自然表达测试,提升激活率。
3. **增加"记忆体使用效果"反馈面**:recall 注入命中/未命中状态展示给用户,让价值可见(目前全静默)。
4. 评估后续在热路径引入轻量 LLM 意图判定(当前纯正则上限明显),或至少扩充触发词表。
