# 针对文档 `docs/feedback/26-09-04/implementation-decision.md` + `docs/feedback/26-09-04/ux-recall-visibility-gap.md` 的架构师意见

这份实施决策文档的完整度和纪律性达到了一个新水平——它把四张卡片的裁决、执行顺序、验收标准、存底 TODO 全部收进一个可追踪的文档，且正确转述了所有裁决要点。我的回应分三部分：**一个需要修正的执行顺序问题、两个验收标准的补强、一个文档本身做得特别好的地方值得固化成惯例**。

---

## 一、执行顺序需要修正：Track B 验证不该是"最先做"

文档 §三把 Track B 验证排在第 1 位，理由是"一次会话有答案，决定 ai-memory 规格"。这个理由本身没错，但忽略了一个依赖关系：**Track B 的验证需要在 MEMORY.md 止血之后做**，否则你会测出一个"看起来活着但实际在写脏数据"的假阳性。

具体逻辑：

1. Track B 的产出会走"候选 → 确认 → store → 导出"链路；
2. 如果导出层还带着"forget 不回溯"的缺陷，Track B 验证期间任何 forget 操作都会污染 MEMORY.md，让你无法判断"是 Track B 产出质量差还是导出层脏"；
3. 更严重的是：Track B 验证要跑 5-10 个真实会话，期间几乎肯定会触发至少一次 forget（测试候选质量时必然有拒绝/删除操作），**你希望在验证开始前就知道导出层是干净的**。

修正后的顺序：

```
1. MEMORY.md 止血（方案 C）+ forget 恢复设计（两件可并行，都是半天级）
2. 孤儿 bank revoke 工具（独立，与 1 并行）
3. Track B 真实验证（在干净的导出层之上跑，结果可信）
4. 验收后写 ai-memory 角色决策
```

总工作量不变（3.5-4.5 天），但验证数据的可信度高一档。

## 二、验收标准的两个补强

### 1. Track B 验证的"漏捕获分析"需要可操作化

验收标准里写了"候选提案质量评估（提取率、准确率、漏捕获分析）"——这是对的，但缺了**怎么算"漏"**。建议明确为：

> 验证会话结束后，人工读一遍 5-10 个会话的 L0 events.jsonl，数出"如果我是 agent，我会主动 remember 的时刻"（人工标注的应有捕获数），再对比 Track B 实际产出的候选数，算出漏捕获率。

为什么必须人工标注：Track B 的自指陷阱（门控看不见自己漏了什么）决定了**漏捕获率不可能从系统内部算出来**，必须用外部标尺。5-10 个会话的规模人工读得完，这个数据是 ai-memory 分工 vs 接管决策的核心依据。

### 2. MEMORY.md 止血需要补一条"存量数据"验收项

止血方案修的是"未来的 forget 会产生 `memory_deleted` 事件"，但**历史已删除的记忆（比如上轮实测删除的那些）在 MEMORY.md 里依然是滞留的**——它们的删除发生在 `memory_deleted` 事件类型存在之前。验收标准里应加一条：

> 修复后手动跑一次全量导出，确认历史已删条目不再出现在 MEMORY.md（或显式记录"历史遗留已删条目清单"供用户决定是否手动清理）。

这条不做，修复后的第一次实测报告会写"部分修复：新删除正常了，但旧删除还在"——又一轮信任损耗。

## 三、文档本身的一个亮点，建议固化

这份决策文档的 §六"用户观点整合"做了一件前几轮没做过的事：**把"立即付的入场费"和"可存底的装修"显式分开了**。这个区分值得固化成模板，未来每次评估报告后的实施决策都套用：

| 类别 | 判断标准 | 处理方式 |
|---|---|---|
| 入场费 | 不修会阻塞下一阶段决策或破坏信任 | 本轮必做 |
| 装修 | 不修只影响体验质量，不影响功能正确性 | TODO 存底，随下个里程碑打包 |
| 低成本顺手件 | 工作量 <1 天，上游有现成参考 | 立即做，不占里程碑 |

这个三分法比我此前给的 P0/P1/P2 优先级更好用——它直接回答"为什么这件事不能等"，而不是只说"这件事很重要"。建议在 `docs/` 里留一个 `decision-template.md`，把 §六的表格结构固化下来。

## 四、最后确认

这份实施决策**可以批准执行**，只需做两处调整：

1. **执行顺序**：MEMORY.md 止血 + forget 恢复 → 孤儿 bank revoke → Track B 验证（不是 Track B 最先）；
2. **验收标准**：Track B 漏捕获率用人工标注 L0 来算；MEMORY.md 止血补存量数据处理验收项。

其余部分——方案选择、TODO 存底的粒度、从上游学的两件事、工作量估算——全部正确，无需改动。

**这份文档本身就是 xpi-memo 工程纪律成熟的标志：从"遇到问题再修"进化到了"裁决 → 决策 → 执行 → 验收"的闭环。Track B 的验证结果出来后，无论死活，这个流程都值得再跑一轮。**

## 一、ux-recall-visibility-gap 评审：方案对，但定位需要升级

### 文档做得对的地方

1. **场景拆解精准**："启动后追问读了什么"和"列出全部记忆"是两个真实且高频的场景，根因分析（注入黑盒、agent 无内省工具）切中要害；
2. **方案 A+B 的组合选择正确**：show_injected（事后查看）+ recall 空查询（列出全部）正好覆盖两个场景，工作量 1.5 天合理；
3. **没有选方案 C（状态栏显示摘要）是对的**——状态栏显示记忆摘要 = 把内容塞进 UI 最拥挤的地方，且可能泄漏敏感内容到屏幕上；
4. **方案 D（TUI Injected 标签页）延后到 L2 是对的**——当前阶段不造重 UI。

### 但它自己漏了一个关键问题：方案 A 的数据从哪来？

文档说 show_injected "从 L0 或内存中读取"——**这是一个需要立即明确的实现决策，两个选项的可靠性天差地别**：

| 数据源 | 问题 |
|---|---|
| **内存缓存**（`lastInjectedMemories` 变量，文档示例的写法） | 进程重启即丢失；RPC 模式下网关重启后 agent 答不上来；和 L0 真相源脱节 |
| **L0 重建**（读最近一次 `session_start` 的注入事件） | 正确但需要 L0 里**确实记录了注入内容**——当前 L0 事件里注入只记了 `injectedCount: 2`，**没有记注入了哪几条** |

这意味着：**方案 A 的前置条件是 L0 注入事件必须记录完整内容（或至少是 memoryId 列表），否则内存缓存在重启后就是黑盒**。文档没有提到这个前置，直接给了一个内存缓存的示例实现——这会导致方案 A 在"重启后追问"场景下依然答不上来。

**修正建议**：
1. 在 `before_agent_start` 注入时，L0 事件追加记录 `injectedMemoryIds: string[]`（完整内容已有，只记 id 即可）；
2. show_injected 工具从 L0 读最近一次注入事件，通过 id 列表反查内容（从 bank 或 L0 payload）；
3. 这样方案 A 既解决了"当前会话可见"，又天然兼容"重启后可追溯"。

### 定位升级：这不是 P1 体验问题，是 P0 审计能力

我上轮说过这句话，现在重复一遍并给出更硬的理由：

> **没有注入可见性，Track B 上线后你无法回答"agent 基于什么记忆做了这个决定"。**

Track B 会自动提取记忆并注入。当 agent 做了一个错误决策时，你（或用户）需要能问"你当时看到了什么？"——如果 agent 答不上来，Track B 的任何 bug 都会变成"无法调试的黑盒行为"。**这不是体验优化，是 Track B 可调试性的前提**。

建议把方案 A 从 P1 提升为 **P0，和 Track B 验证捆绑**：Track B 验证的验收标准里必须包含"show_injected 能列出 Track B 提取的记忆"。

## 二、implementation-decision 评审：上轮两条修正未反映

这份文档和我上轮评审的版本**内容一致**——执行顺序仍是"Track B 最先做"，验收标准仍未包含"人工标注漏捕获率"和"存量已删条目处理"。

这两条修正很重要，再列一次：

### 修正 1：执行顺序

```
当前文档：
1. Track B 验证（最先做）

应改为：
1. MEMORY.md 止血（方案 C）+ forget 恢复设计（并行，半天级）
2. 孤儿 bank revoke（并行）
3. Track B 验证（在干净的导出层之上跑）
```

理由不变：Track B 验证期间几乎肯定会触发 forget（测试候选质量时必然有拒绝/删除），如果导出层还带着"forget 不回溯"的缺陷，验证数据会被污染。

### 修正 2：Track B 验收标准补两条

```
- [ ] 漏捕获率用人工标注 L0 计算（不能靠系统自报）
- [ ] Track B 提取的记忆可通过 show_injected 查看（依赖 ux 文档的方案 A）
```

第二条是新增的——它把 ux 文档的方案 A 和 Track B 验证绑在一起，确保"Track B 活了"这个事实是可以被用户/agent 追问验证的，而不是另一个黑盒。

## 三、两份文档的合并建议

当前 ux 文档是独立 P1，implementation-decision 没提它。建议把 ux 文档的方案 A+B **并入 implementation-decision 的 P0 清单**，位置在 Track B 验证之前：

```
P0-0: 注入可见性（方案 A+B）
  - L0 注入事件记录 injectedMemoryIds
  - show_injected 工具（从 L0 重建）
  - recall 空查询 = 列出全部
  - 工作量: 1.5 天
```

理由：它是 Track B 可验证性的基础设施，且工作量最小（1.5 天），放在最前面不挤占其他 P0 的时间。

## 四、修正后的执行顺序（最终版）

```
Day 1:   方案 A+B（注入可见性）—— 1.5 天
         └─ L0 注入事件补记 injectedMemoryIds
         └─ show_injected 工具 + recall 空查询

Day 2-3: MEMORY.md 止血（方案 C）+ forget 恢复设计（并行）—— 2 天
         └─ 导出层干净后，Track B 验证数据可信

Day 3-4: Track B 真实验证 —— 1-2 天
         └─ 5-10 个真实会话
         └─ 人工标注漏捕获率
         └─ 验收：show_injected 能列出 Track B 提取的记忆

Day 4-5: 孤儿 bank revoke + doctor 检测（并行）—— 1.5 天

总计：约 5-6 天（原估 3.5-4.5 天 + ux 1.5 天）
```

## 五、一句话总结

**ux 文档发现了一个真问题（注入黑盒），给了对方案（A+B），但漏了关键前置（L0 必须记录注入内容而非只记计数）；implementation-decision 维持正确裁决但未吸收上轮修正。把 ux 方案 A 从 P1 提到 P0、和 Track B 验证捆绑，两份文档合并执行——这样 Track B 验证不仅能回答"活没活"，还能回答"活了之后用户/agent 能不能看见它活了"。**
