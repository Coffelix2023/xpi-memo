# 针对`docs/feedback/26-09-04/feedback-0904-1.md`报告的评审意见

这份报告是四次实测里最有价值的一次——不是因为发现了新 bug，而是因为它**第一次把四个看似独立的症状归因到了同一个架构级根因上**。我先给这个根因命名，然后逐项拆解，最后给出和前几轮不同性质的判断。

---

## 一、总体结论：xpi-memo 的病不在功能，在"证据链脱钩"

前三次实测的病是"治理病 → 捕获病 → 注入语言错配"，都是功能层缺陷，修一行代码能止血。这一次的四个症状（`t1_memory_write` 事件为 0、MEMORY.md 恒空、自动捕获 0 产出、非 TUI 候选无人确认）表面上分属不同子系统，但共享同一个根因：

> **xpi-memo 的"治理确认路径"和"证据/产物生成路径"是两条平行线，前者可以成功后者的产物却是空的。**

具体说：`candidate_confirmed` 事件发生了（8 条）、gist 落库了（8 条）、但 `t1_memory_write` 事件是 0、MEMORY.md 是空——**确认成功了，但确认这个动作没有触发它应该触发的下游产物**。这不是"少发了一个事件"的小错，这是一个架构信号：**系统的状态转移和状态转移的记录不是原子操作**。

为什么这很严重：你的整个设计哲学是 L0 事件溯源（events.jsonl 是 append-only 真相），MEMORY.md、audit、doctor 都应该是 L0 的派生视图。但 `index.ts:946` 的发射点和实际 store 路径脱钩，意味着**L0 并不是完整的真相源**——有些真实发生的状态转移（确认→落库）没有留下 L0 事件。一旦"L0 不完整"成立，所有派生视图（MEMORY.md、未来的 reindex、跨机器回流）的可信度都归零。

## 二、逐项拆解：哪些是同一根因，哪些是独立问题

| 症状 | 根因归属 | 性质 |
|---|---|---|
| `t1_memory_write` = 0 → MEMORY.md 恒空 | **证据链脱钩**（确认路径不发事件） | 架构级 |
| 自动捕获 0 产出（25887 事件仅 8 候选，全手动） | **Track B 未真正激活**（报告标注 v1.0.0-16 含 gated Track B，但 0 自动捕获说明门控条件未触发或 Track B 未接入 activation loop） | 配置/接入级 |
| 非 TUI 候选 `return "later"` → 无人确认 | **治理双闸门的幽灵回来了**（第一次实测的老问题，在非 TUI 下复发） | 设计级 |
| 非 git 目录 project bank recall 不可达 | 上轮已判 P1，`/xpi-memo-init` 机制存在但用户没用 | 设计级（有机制，未触达） |
| sleep 无降级 | 上轮已判 P1，本轮复现 | 未修复项 |
| 重复偏好共存（`supersededBy` 空转） | 遗忘/去重机制未被触发 | P2，新发现 |

关键判断：**第 1 和第 3 条是同一个架构问题的两面**——确认路径既不发 `t1_memory_write`（产物丢失），也在非 TUI 下把候选永远挂起（状态丢失）。它们共享一个假设："确认这件事一定发生在 TUI 交互里"。一旦这个假设不成立（RPC 模式、自动化、headless），确认路径的下游全部断裂。

## 三、必须单独说的：Track B 在哪里？

报告第一行标注版本是 `v1.0.0-16-g73e25d0（含 gated Track B 提取）`，但 25887 条事件里 0 自动捕获。这有两种可能：

1. **Track B 的门控条件没触发**（比如：门控条件是"正则轨道漏捕获率 >30%"，但这个统计本身需要 `no-explicit-intent` 事件被记录，如果漏捕获根本没被记录，门控永远看不到自己的触发条件——**自指陷阱**）；
2. **Track B 激活了但没接入 activation loop**（提取逻辑存在，但 hook 没挂到 session_shutdown / compaction 边界）。

无论哪种，这都是一个**"功能存在但不可达"**的问题，和 `t1_memory_write` 的"成功但无证据"是同一族。建议在下一轮实测里加一个专门的验证项：手动触发一次 Track B 提取（跳过门控），确认提取管道本身能产出候选——这能把"管道坏了"和"门控没开"区分开。

## 五、决策与下一步

### P0（本周，修证据链原子性）

1. **把"确认→落库→发事件"包成一个原子操作**：`confirmCandidate` 内部必须在同一事务里完成三件事——mnemosyne store、`t1_memory_write` L0 事件、MEMORY.md 增量更新。任何一个失败，整个确认回滚。这根治的不只是 MEMORY.md 空，而是"L0 不完整"的信任危机。
2. **非 TUI 候选的自动确认策略**：`chooseCandidateAction` 的 `return "later"` 在非 TUI 下等于"永远不确认"。改为：非 TUI 模式下，高置信候选（`explicit-user-statement` 证据类型）直接自动确认，低置信（`llm-extracted`）进队列等下一次 TUI 会话。**把"TUI 确认"从治理的必要条件降级为治理的偏好条件**——这是第一次实测就该做的修复，现在数据够了。

### P1（两周内，激活 Track B + 验证管道）

3. **Track B 可达性验证**：手动触发一次提取，确认管道能产出候选；然后检查门控统计逻辑是否能"看见"正则轨道的漏捕获（如果漏捕获不产生可统计的事件，门控是瞎的）。
4. **sleep 降级**：`XPI_MEMO_SLEEP_MODEL` 未配置时，允许 `sleep --mechanical` 模式只做去重/合并/过期清理，不做语义压缩。

### P2（结构性，随 L2 一起）

5. **遗忘/去重机制激活**：`supersededBy` 字段存在但从未触发，3 条重复偏好共存。这和 sleep 的机械合并是同一个功能——去重不是"高级功能"，是记忆体的基本卫生。
6. **非 git 目录的 recall 范围**：`/xpi-memo-init` 机制已存在但用户感知不到。在 `routing_rejected` 事件发生时，下一个 assistant 回复应该主动提示"是否初始化项目记忆"，把机制推到用户面前。

### 止损线再校准

上一轮我把止损条件定义为"Track B 上线后注入命中率"。本轮数据说明 Track B 可能根本没真正跑起来——所以止损条件修正为：**P0 两项修复后，下一次实测必须同时满足：(a) `t1_memory_write` 事件数 = `candidate_confirmed` 事件数（证据链闭合）；(b) 至少 1 条自动捕获的候选（Track B 产出）；(c) MEMORY.md 非空**。三条都过，xpi-memo 从"手动便签本"毕业；任何一条不过，ai-memory 外挂方案的评估自动启动。

## 六、一句话总结

**xpi-memo 前三次修的是"记忆从哪来"（捕获、治理、注入），这次暴露的是"记忆去哪了"（证据链断裂导致产物丢失）——前者是血肉，后者是骨骼。骨骼不修，血肉补得再好也立不起来。** 优先修原子性，让"确认"这个动作同时意味着"被记录、被导出、可被召回"，然后 Track B 才有意义——否则自动捕获产出的候选，照样会消失在证据链的裂缝里。
