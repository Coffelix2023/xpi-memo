# 针对`plans/plan-note-01.md`计划的评估报告:

这份方案我读完了。总体判断：**工程质量意识一流，但保守性错位——它把上一轮诊断出的"零记忆稳态"治好了，却用一种过度防御的方式治疗，可能在下一个阶段制造出新的稳态问题（记忆贫瘠 + 提取器维护地狱）**。分层评估如下。

## 一、做对了什么（值得明确肯定）

1. **不动骨架，只修断点**——保留 L0 事件源、Bank 路由、七类闭合分类、候选生命周期，符合上一轮"不要推翻架构"的判断。四个断点的定位全部准确，尤其是抓到了两个真正的代码级 bug：`before_agent_start` 硬编码 `high-value-auto` 导致配置失效（召回断点），以及 `operationFor` 把所有工具输入伪装成 `explicit-user-statement`（证据断点）——**后者是真正的治理漏洞，比零记忆更严重**：Agent 的推断被当成用户明示，一旦自动存储就是污染源头。把它修掉（"source 仅作来源描述，不再决定证据类型"）是全文最有价值的一条。

2. **幂等去重 + 审计不含正文 + 非 Git 目录拒绝静默写全局库**——这三条是生产级的细节，多数记忆系统会在上线三个月后才被迫补上。

3. **验收标准里明确拒绝"20~50 条记忆"这类虚荣指标**，改用捕获/候选/召回/拒绝的计数比率——这是对的度量观。

## 二、核心分歧：确定性关键词提取器是方案里最大的结构性风险

Slice 1 选择"**无模型、确定性、基于关键词的显式指令提取器**"作为捕获修复的主力，我理解它的动机（可回链、可测试、零成本、可预测），但它有三个被低估的代价：

**1. 召回率天花板极低，且中英双语让维护成本翻倍。** "记住/偏好/以后/始终/踩坑/不要忘"这类触发词列表，捕获的是**用户教学式的显性表达**——但真实对话里有价值的记忆信号大多不这么说话："别再用 npm 了"（纠正）、"这个上次不是这么处理的"（隐含偏好）、"就按上次那个方案来"（连续性引用）。关键词提取器对这些全部沉默。**你等于修好了"agent 不主动调用"的断点，又用关键词列表建了一个新的、更隐蔽的断点**。方案自己在验收里写了"普通陈述、歧义陈述均不误存"——注意措辞：目标是"不误存"，而不是"该存的存到了"。**测试套件在度量假阳性，没有度量假阴性**，而记忆系统的死法恰恰是后者。

**2. "无模型"省下的成本是伪节省。** 方案的兼容性条款写着"不引入 LLM 摘要"和"不启用 sleep（没有已验证专用模型时继续拒绝）"——这两条把一个事实掩盖了：**提取管线的 LLM 成本可以压到接近零**（session 结束时用 cheap model 跑一次提取，一次会话一次调用，pi-memory 的 exit summary 已经证明这条链路存在且便宜）。确定性提取器的真实动机应该是"显式指令的路径必须零幻觉"，而不是"全系统不能有 LLM 提取"。

**3. 它把"冷启动"问题原样保留了。** 关键词提取器只能捕获用户明确说"记住"的场景——而当前用户从未说过（所以才零记忆）。改造后的系统捕获率会从 0/周 提升到也许 2~3/周，**依然达不到让 recall 体验产生质变的密度**（经验阈值大约是 50 条有效记忆以上）。

## 三、修改建议：从"确定性单轨"改为"双轨提取"

保留 Slice 1 的确定性提取器（它作为显式指令的快速路径是完全正确的），但**增加第二条 LLM 提取轨**，两者共用同一套治理、provenance 和候选生命周期：

```
轨道 A（已有）：关键词/模式匹配 → 显式指令 → 直接落盘（零确认）
轨道 B（新增）：session 结束/compaction 时，cheap model 对 L0 events.jsonl
              做一轮事实提取 → 输出 {内容, kind, evidence 回链, confidence}
              → 高置信(>0.8) + 低风险类别 → 直接落盘
              → 其余 → 候选（走现有 Pending inbox，不弹窗）
```

关键约束（回应方案的担忧）：
- **轨道 B 的输出绝不携带 `explicit-user-statement` 证据类型**，统一标 `llm-extracted` + evidence 回链到 L0 event position——证据断点修复对两条轨道同样生效；
- **去重在轨道 B 上是向量级的**（候选指纹之外加 embedding 相似度合并），否则每周 digest 会堆重复项；
- **不做自动覆盖/复杂遗忘曲线**——方案"明确不做"清单里的这一条我同意，保持不变。

这个改法不违反方案的任何架构约束（不加外部依赖、不改候选语义、不动数据根），只把"不引入 LLM 摘要"这条自我设限放松为"**不在热路径引入 LLM；离线提取可以用**"。

## 四、其他需要调整的点（按优先级）

| # | 方案条款 | 问题 | 建议 |
|---|---|---|---|
| 1 | 非 TUI 候选"返回 candidate + Pending inbox 提示" | **Pending inbox 是被动机制，等于换一个地方继续积压**——当前零记忆的部分原因就是候选无人审核 | 加**主动 digest**：每 N 会话或每周，在会话启动时注入一条"你有 5 条待审核候选"的轻提示（非弹窗，纯文本），附一键批量 Store/Reject 命令 |
| 2 | 默认召回改为 `active`，但"每阶段最多一次检索" | 方向对，但 `active` 需要防注入膨胀 | 补上 pi-memory 式的**字符预算**（总注入 ≤ 16K 字符、单条截断）和 **recency 衰减**，方案目前只提了 limit 和截断，没有衰减——库里记忆多了以后，无衰减的 active 会把陈旧记忆顶在前面 |
| 3 | "显式低风险偏好直接落盘"的类别清单 | 只覆盖了 `global_preference/global_workflow` | 建议把**用户纠正（correction）**单独列为最高优先级信号（"不是 X，是 Y"句式）——这是所有生产记忆系统里价值密度最高的记忆类型，当前七类分类里没有它的明确归属，建议归入 `global_workflow` 或 `project_gotcha` 并给最高 importance |
| 4 | `session_context` ≤500 字符超限即拒绝 | 拒绝 = 数据丢失 | 超限应降级为候选或自动截断存 L0 引用，而不是拒绝 |
| 5 | 存储拓扑"三表面并存"只诊断不治理 | 合理（不做自动迁移是对的） | 但建议在 doctor 输出里加**显式警告级别**：当裸 CLI 根与扩展根都有数据时标红——这是用户最容易丢记忆的场景 |
| 6 | 验收缺一项 | 无 | 加一条回归验收：**连续 3 个会话后，人工抽查 10 条自动落盘记忆的 evidence 回链全部可点击定位到 L0 原文**——provenance 是这个系统的差异化资产，要当成功能验收，不是顺带检查 |

## 五、总评

| 维度 | 评分 | 说明 |
|---|---|---|
| 断点诊断 | ★★★★★ | 四个断点全部命中，证据断点的发现是亮点 |
| 架构约束 | ★★★★★ | 不动数据根、不改候选语义、兼容解析，教科书级保守演进 |
| 捕获修复 | ★★☆☆☆ | **确定性提取器单轨制是最大短板**，会制造"修好了但依然贫瘠"的第二稳态 |
| 治理设计 | ★★★★☆ | 例外治理思路对，但 Pending inbox 仍是被动积压；缺 digest 主动化 |
| 召回修复 | ★★★★☆ | 修 bug 准确，但缺衰减与预算的完整设计 |
| 可验收性 | ★★★★☆ | 度量观正确，缺假阴性度量与 provenance 回归 |

**一句话**：按这份方案实施，系统会从"永远零记忆"变成"只在用户说'记住'时才有记忆"——及格但贫瘠。把 Slice 1 升级为双轨提取（确定性快轨 + LLM 离线慢轨）、给 Pending inbox 加主动 digest、给 active 召回加衰减和预算，这份方案就从"修复断点"升级为"真正的生产级记忆系统"。
