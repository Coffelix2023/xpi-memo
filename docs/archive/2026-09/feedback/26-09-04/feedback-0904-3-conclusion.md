## 二、核心新缺陷：forget 不回溯 MEMORY.md——这不是 bug，是架构矛盾的显形

报告 §4 的根因分析非常准确，但我要指出它比报告描述的更深一层：

```
设计 A：MEMORY.md 从 L0 append-only 事件流重建
    → L0 是不可变的 → "删除"无法表达 → 已删条目永久滞留

设计 B：forget 往 L0 追加一条 delete 事件，重建时按 id 剔除
    → 可行，但"人读层"的内容开始依赖复杂的事件重放逻辑
```

这正是我此前反复强调的**"Markdown 真相源 vs SQLite 真相源"哲学分歧**的第一次具象化爆发。现在的架构是"L0 是真相源，MEMORY.md 是 L0 的投影"——但 L0 是 append-only 日志，**日志的语义是"历史发生了什么"，而 MEMORY.md 的语义应该是"现在记住什么"**。这两个语义在删除操作上不可调和：日志里"曾经写入然后删除"是两条事实，而人读层应该什么都不显示。

**我的明确建议（比报告的两个修复方向更进一步）：MEMORY.md 改为从 bank（SQLite 当前状态）重建，而不是从 L0 重建。**

理由：
1. **语义对齐**：MEMORY.md 是"当前记忆状态的人读视图"，bank 才是"当前记忆状态"的权威存储；L0 是审计/溯源层，回答"怎么变成这样的"。视图应该投影状态，而不是投影历史；
2. **删除、supersede、合并天然正确**：从状态重建，forget/supersededBy/mechanical sleep 去重的结果自动反映，不需要为每种变更事件写投影逻辑；
3. **复杂度反转**：现在是"每个写入/删除路径都要记得发对事件，否则视图就错"（本轮 forget 就是漏网证明）；改后是"重建逻辑只有一个入口，写路径爱发什么发什么"。**这正是上一轮 outbox 改造的同一个教训——把正确性从'每个调用点各自努力'改为'单一路径天然正确'。**

过渡期兼容方案（低成本）：在 `collectMemoryEntries` 里处理 forget/delete 事件按 id 剔除（报告建议的方向 1），作为止血；同时在代码里标注 `// TODO: MEMORY.md 数据源切换为 bank 重建`，把方向 2 作为 L2 工作的一部分（它与"SQLite 可重建/Markdown 真相源"升级是同一包工作，那时反而顺理成章：**bank 是可重建的索引，Markdown 是真相源——两个投影方向都要翻转**）。

Answer:

## 一、验收表：ai-memory 前置条件逐项核对

引入 ai-memory 的本质是：**把 xpi-memo 的固化产物导出为跨 harness 的 wiki 真相源，并让 ai-memory 承担捕获/合并的重活**。这要求 L0/T1 提供四样东西：

| # | ai-memory 需要的前置 | 当前状态 | 判定 |
|---|---|---|---|
| 1 | **L0 是完整可信的事件真相源**（ai-memory 的回流/审计要能对账） | `t1_memory_write` 已贯通、事件链完整、outbox+coordinator 统一了副作用路径 | ✅ 满足 |
| 2 | **T1 记忆有完整元数据**（kind/scope/bank/evidence/fingerprint，导出 wiki 页时要带） | 7-kind 封闭类型、证据类型、provenance、幂等指纹全部实测在 | ✅ 满足 |
| 3 | **导出层是"当前状态的投影"，可幂等重放**（ai-memory 的单向同步依赖这个） | ❌ **不满足**——forget 不回溯 MEMORY.md 刚证明了"L0 历史投影 ≠ 当前状态"；同步给 ai-memory 的内容会带着已删除的记忆 | 🔴 空心 |
| 4 | **捕获管道的角色边界已划分**（Track B vs ai-memory 的 hooks 捕获，谁干什么） | ❌ **不满足**——Track B 连续三轮零验证数据，它是否活着未知；不知道它的产出质量，就无法决定 ai-memory 是"分工"还是"接管" | 🔴 空心 |
| 5 | 安全边界（secrets/PII 拦截） | token/API key 拦截实测通过，audit 不落内容拷贝 | ✅ 满足——且 ai-memory 侧有自己的 typed privacy boundary，双层防护 |
| 6 | 多 bank 生命周期 | 孤儿 bank 检测/归档未做，但 ai-memory 按项目 wiki 组织，不依赖你的 bank 拓扑 | 🟡 不阻塞 |

## 二、两个空心项为什么在引入 ai-memory 之前必须补上

**空心项 #3（导出层语义）会被 ai-memory 放大。** 现在 MEMORY.md 错了只影响你一个人看本地文件；一旦 ai-memory 的单向同步跑起来，**已删除的记忆会被推送到跨 harness 的共享 wiki，被 Claude Code/Codex 召回**——删除失效从"本地视图瑕疵"升级为"跨工具的记忆泄漏"。而 ai-memory 那边的 wiki 是 git 版本化的，删进去的东西再清就难了。所以上轮说的"MEMORY.md 从 bank 状态重建"不是可选项，是引入 ai-memory 的**硬前置**。

**空心项 #4（Track B 生死未卜）决定 ai-memory 的角色定义。** 回顾我们定的决策树：Track B 活 → ai-memory 只做"跨 harness 骨干网"（分工）；Track B 死 → ai-memory 接管 L2 捕获→合并（接管）。**不验证 Track B 就开工，你连 ai-memory 的接入规格都写不出来**——接口画在哪一层（导出同步层 vs 捕获接管层）取决于这个答案。

## 三、结论与开工顺序

**L0/T1 可以宣布"地基验收有条件通过"。进入 ai-memory 阶段前，按此顺序关两个闸：**

1. **闸门 A（一周内可关）**：导出层数据源切换——MEMORY.md 及未来的 ai-memory 同步出口统一改为"bank 当前状态投影"，forget/supersede 天然正确。这是纯内部重构，测试已有基础。
2. **闸门 B（一次实测可关）**：Track B 真实验证（开启 → 真实会话 → 看候选产出和五态诊断）。结果直接决定 ai-memory 接入规格书写哪种角色。

两闸关完，你手里就有了写《ai-memory 接入规格》所需的全部事实：**可信的 L0、元数据完备的 T1、语义正确的导出层、明确的角色边界**。届时接入工作会顺利得多——而且无论 Track B 死活，这两条闸门的产出都不浪费。

反过来，如果现在跳过闸门直接接 ai-memory，最大的风险不是技术失败，而是**把两套系统的边界糊掉**：xpi-memo 的治理哲学（高置信、证据分级）和 ai-memory 的捕获哲学（静默、全量）一旦在数据层面混流，分开它们的成本会比现在补两个闸门高一个数量级。
