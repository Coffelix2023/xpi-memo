# 针对`plans/plan-note-02.md`计划的评估报告:

方案2读完了。先说总体判断：**这是一份比方案1更成熟的"战略层"文档**——定位取舍清晰、许可证边界专业、竞品分析扎实，而且有意修正了方案1 的两个主要短板（召回侧补上了 standing/contextual 分离、意图加权、衰减、去重；冷启动明确不赌"用户会说记住"）。但它身上有一个比方案1 更隐蔽的风险：**在写入侧坚持了方案1 被我指出的最大短板（无模型确定性提取），并且这次把它制度化进了"明确不做"清单（§8.5）**。分层评估如下。

## 一、方案2 相对方案1 的真实进步

| 维度 | 方案1 | 方案2 | 评价 |
|---|---|---|---|
| 召回侧 | 只修硬编码 bug + 默认 active | standing/contextual 分离 + 意图加权 + 排序公式 + 预算 | **结构性升级**，直接回应了我上一轮提的"加预算、加衰减" |
| 冷启动 | 无专项 | 明确不赌用户显式表达 | 方向对，但解法仍有问题（见下） |
| 许可证 | 未提 | MIT 可移植 / GPL 只借思想 / THIRD_PARTY_NOTICES | 专业，多数团队上线一年后才补 |
| 度量 | 计数型指标（好） | 同一套 + `有价值捕获率 × 有效召回率` 乘积公式 | 乘积公式是全文最有价值的一句话——它承认了"捕获和召回是串联的，任一为零则全盘为零" |

特别值得肯定的三处设计：

1. **standing/contextual 分离 + 4~5K 字符预算**——这是我上一轮建议的"字符预算制"的正确实现形态，而且比 pi-memory 的固定注入更精细（区分常驻记忆与情境记忆，情境记忆按查询意图加权）。
2. **排序公式 `relevance × confidence × recency × scope × diversity`**——把治理后移到 recall 的完整落地，且明确"记忆数量增长后才引入 MMR"，避免了过度工程。
3. **§8.4 "目标不是最大化行数，而是最大化 有价值捕获率 × 有效召回率"**——这句话应该写在 README 第一行。

## 二、核心分歧：§8.5 把"不用 LLM 提取"从战术选择升级成了制度承诺

方案1 里确定性提取器只是一个 slice 的实现选择；方案2 的 §8.5 把它写进了"明确不做"清单，措辞是"第一阶段不加入模型摘要器……后续**如果数据证明规则覆盖不足**，再评估"。问题在于：

**1. 这个"数据证明"的条件在你的设计下永远不会被触发。** §5.1 的关键词示例（"记住：""请记住""以后不要"）和方案1 几乎一样——这只能捕获"用户教学式表达"。而你自己在 §2.2 引用的三条不足里，第一条就是"Agent 不主动调用 remember 就没有 T1"。**关键词提取器修复的是"用户说了记住但系统没接住"，不是"用户从来不说记住"**。当前零记忆的根因是后者。更矛盾的是：要"用数据证明规则覆盖不足"，你需要先统计"漏掉了多少本该捕获的记忆"——但漏掉的内容从未进入系统，你拿什么统计？这是一个**不可观测的假阴性**，度量体系（§7.3 的计数指标全部是正向计数）天然测不到它。

**2. §5.4 的"agent_end 捕获"是全文最别扭的一条。** 它借了 mnemopi 的触发时机，却规定"扫描显式记忆意图（关键词），高置信度写入"——等于在正确的时机跑了一个错误的扫描器。mnemopi 在 agent_end 做的是**事实抽取（LLM-driven）**，你只借时机不借机制，这条路径的产出会和热路径关键词提取器几乎完全重合，形同虚设。

**3. "省成本"的理由在本场景不成立。** pi 的会话本来就有 compaction 和 exit 这两个既有 LLM 调用点，提取可以搭便车（在 compaction summary 的 prompt 里加一段"同时列出本轮值得跨会话留存的事实"，几乎零增量成本）；即便独立调用，一次会话一次 cheap model 提取，月成本在个位数美元量级。为了省这个钱，付出的是**系统的核心功能（自动记忆）实质性缺席**。

**我的修改建议**：把 §8.5 从"明确不做"降级为"**P1  gated 能力**"，并给出明确的触发条件而不是"数据证明"这种不可测措辞：

```
LLM 离线提取（轨道 B）：
- 触发时机：compaction / session_shutdown（搭既有调用便车，热路径零增量）
- 输出：{content, kind, evidence 回链, confidence}，证据类型一律 llm-extracted
- 路由：confidence > 阈值 + 低风险 kind → 直接落盘；其余 → candidate
- 开关：config 可关，预算封顶（每会话最多提取 N 条）
- 上线条件（gated）：轨道 A 运行 2 周后，人工抽查 20 个会话的 L0，
  若"关键词未捕获但人工判断应记忆"的比例 > 30%，即启动轨道 B
```

这样既保留了方案2 的谨慎（先跑纯确定性轨道收集证据），又给"数据证明"一个可操作的定义，避免它成为无限期拖延的借口。

## 三、其他需要调整的点（按优先级）

| # | 条款 | 问题 | 建议 |
|---|---|---|---|
| 1 | §5.3 候选管理：新增 `/xpi-memo-candidates` 命令 | 比方案1 的"被动 Pending inbox"好（有了管理入口），但**仍是拉取式**——用户不主动敲命令，积压依旧 | 加一行：**每次 session_start 若候选 > 5 条，注入一条纯文本提示**"有 N 条待审核记忆，运行 /xpi-memo-candidates 处理"（非弹窗，零打断） |
| 2 | §6.1 "无高分结果：不注入 memory block" | 对 | 但需补 KV-cache 条款：注入块必须**位置固定 + 无结果时整块省略**（而不是注入空块），否则每轮前缀字节不稳定，缓存全废——pi-memory 的稳定快照机制就是为此存在，方案在 §9 阶段三才提"稳定快照"，建议提前到阶段一，与召回上线同步 |
| 3 | §5.1 提取器对"纠正"类信号无专门处理 | 我上轮提过：用户纠正（"不是 X，是 Y"）是价值密度最高的记忆信号 | 在关键词集里单列 correction 模式（"别再用"/"上次不是"/"actually"/"不对"），命中后 importance 直接给最高档——纠正类记忆被覆盖的代价远大于普通偏好 |
| 4 | §7.2 恢复删除"如实现成本可控再增加 restore" | forget 有 recovery 但无 restore = 恢复能力是摆设 | recovery record 已存全量 payload，restore 只是一个 INSERT，成本极低，建议与 forget 同阶段交付 |
| 5 | §6.2 预算"standing 3 条 / contextual 3~5 条" | 合理起点 | 补充：条数上限与字符预算应**双约束取严**，且 standing 内按 kind 设配额（preference 最多 2 条等），防止单一类别挤占 |
| 6 | §3 自身无 LICENSE | 已识别 | 提前解决，别等"正式发布前"——第一天没有 LICENSE 的私有仓库，后续补证第三方声明的成本只会更高 |

## 四、两份方案的关系与合并建议

方案1 和方案2 不是替代关系，是**同一次修复的战略层（2）与战术层（1）**：

- **从方案2 继承**：定位取舍、许可证边界、standing/contextual 分离、排序公式、度量公式、三阶段路线；
- **从方案1 继承**：证据断点修复（`operationFor` 不再伪装 explicit-user-statement——方案2 居然没有提这个 bug 的修复，这是方案1 独有的关键贡献，**必须保留**）、幂等去重、非 Git 目录拒绝静默写全局、测试套件的具体用例；
- **两份共同修正**：确定性提取从"唯一轨道"降级为"轨道 A"，新增 gated 的 LLM 离线提取轨道 B；候选管理从拉取式升级为"拉取 + session_start 轻提示"；召回上线与 KV-cache 稳定快照同步交付。
